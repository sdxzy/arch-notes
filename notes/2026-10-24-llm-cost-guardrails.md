# LLM 费用失控护栏：一个 Agent 死循环烧掉整月预算

> 10-24 晚的架构对练。一个场景问到底：护栏放哪几层、速率类和额度类限制为什么要分开处理、断路器的状态存哪、队列满了怎么办。附一个离线可跑的 TS demo（run 级上限、预占+结算、有界公平队列、断路器、原子状态存取）。

## 1. 场景

你做了一个 Agent 产品，按 token 给 LLM 供应商付钱。某天早上一看账单：

- 有个用户的 Agent 卡在「**调工具 → 报错 → 让 LLM 重试**」的循环里，跑了一整夜；
- 一个人烧掉了整个月的预算；
- 因为共用同一个 key，**其他用户也开始被 429 限流**。

问题：护栏放在哪一层？先加哪一层？只加这一层，哪种坏情况还是拦不住？

## 2. 讨论过程：Dong 的想法与补充

### 2.1 第一反应：加在任务维度，重试次数过多就失败

> **Dong 的想法**："我的想法是加在任务维度，如果一个任务重试次数过多就应该失败。"

**点评：方向对。** 死循环就是在 run（一次任务）这一层转起来的，所以单 run 是最该先加的一层。但只数重试次数有两个漏洞：

- **没有报错的循环。** 工具调用都成功，LLM 却一直重复同一个动作，重试计数永远是 0，拦不住。所以 run 的上限要按**总步数、总 token、总花费、总时长**来设，再加**重复动作检测**；
- **多个 run 叠加。** 每个 run 都只花一点点，但同一个用户一晚上开了 500 个 run（或者定时任务每次失败后自动新建一个 run），总数照样烧穿预算，还会把其他人挤到 429。这一层要靠**用户/租户级预算**；全局预算只当最后一道保险。

> **补充：** 供应商控制台里的月度硬上限和 50%/80%/100% 告警是更外面的一层兜底，不是你代码里的护栏，但一定要开。你自己的护栏有 bug 的时候，它是最后一道线。

### 2.2 追问：定时任务每次失败都自动新建 run，拦在哪层？

**追问：每个 run 都有上限，但某个用户的定时任务每次失败后又自动新建一个 run。你会在哪一层拦住它？拦住的时候是直接拒绝、排队，还是降级成便宜的模型？**

<details><summary>参考答案</summary>

- 拦在**用户/租户层**（额度类）加上**触发源层**（断路器）；
- 速率类限制（并发、TPM）会恢复 → 排队或等待；
- 额度类限制（日/月预算）不会很快恢复 → **直接拒绝**，返回明确的「额度已用完」；非关键任务可以降级到便宜模型；
- 再加一个**断路器**：同一个触发源连续失败 N 次就暂停这个调度，并通知用户，不要继续建新 run。

</details>

> **Dong 的想法**："我理解是排队？"

**点评：对了一半。** 关键是先分清两种限制（详见第 5 节）：

- **速率类**（并发数、每分钟 token）过一会儿就恢复，排队是对的；
- **额度类**（本月预算、每日花费）是累计的，到重置前都不会恢复。排队没有意义：队列只会越堆越长，等额度一重置又一起放出去，**反而造成新的尖峰**。应该直接拒绝。

### 2.3 Dong 插问：连续失败 N 次，记录在哪里？内存吗？

> **Dong 的想法**："如何记录一个用户同一源连续失败 N 次，记录在哪里呢？内存里吗？"

**点评：不建议只放内存。** 服务重启或多实例部署时会丢失或不一致，而断路器要的恰恰是跨重启、跨实例的记忆。这是一个很好的插问，本质上是「状态放哪」的取舍，详见第 7 节。

### 2.4 追问：队列要不要设上限？到了上限怎么办？

> **Dong 的想法**："设置上限，如果达到上限就先拒绝？"

**点评：对。** 队列要有长度上限和等待时间上限，满了就快速拒绝，并告诉调用方多久以后可以重试（`429` 加 `Retry-After`）。这叫**背压（backpressure）**，不然队列会无限长，内存和延迟都失控。这个结论是 Dong 自己得出来的。

## 3. 四层护栏：各管什么

| 层 | 管的是 | 典型上限 | 超限时 | 拦不住什么 |
|---|---|---|---|---|
| **① 单步**（一次 LLM 调用） | 单次请求别太大 | `max_tokens`、输入裁剪、单次超时 | 截断 / 报错 | 一万次小请求 |
| **② 单 run**（一个任务） | 一个任务别无限转 | 步数、花费、token、总时长、重复动作、工具连续报错 | 终止 run | 开 500 个 run |
| **③ 用户/租户** | 一个人别烧光大家的 | 并发数、日/月预算、队列份额 | 速率类排队/拒；额度类拒 | 全体用户同时涨 |
| **④ 全局** | 整个产品别爆预算 | 全局日预算、总并发、供应商硬上限 | 拒绝 / 降级 / 人工介入 | 已经烧完才触发 |

读法：**死循环发生在 ②，所以先加 ②；但「一个人」造成的损失由 ③ 封顶；④ 是保险，不是主防线。** 只加 ②，拦不住多 run 叠加；只加 ④，等触发时预算已经没了，而且所有人一起被拒。

## 4. 单 run 护栏：别只数重试

死循环有几种形态，每种要的探测手段不同：

| 循环形态 | 只有「重试次数上限」 | 能拦住它的是 |
|---|---|---|
| 工具报错 → LLM 重试 | ✅ 能拦 | 工具连续报错上限（Dong 的想法） |
| 工具成功，LLM 重复同一动作 | ❌ 重试计数是 0，拦不住 | **重复动作检测**（同工具+同参数连续 N 次） |
| 参数每次不同（带时间戳/计数器） | ❌ | 重复检测也被绕过 → **总步数上限**兜底 |
| 每步都很贵（大上下文） | ❌ | **总花费/总 token 上限** |
| 每步都很慢 | ❌ | **总时长上限** |

两个细节：

- **花费上限要在调用前判断。** 用「已花 + 本步最坏情况（输入 + `max_tokens`）」去比较，超了就不发请求，这样实际花费永远不会越过上限；
- **重复检测是启发式，会误判也会漏判。** 它只能当「早一点停」的手段，总步数/花费/时长这三个**硬上限**才是底线。

> 补充：run 被护栏终止后，别让调度层又自动新建一个 run 来「接着做」，否则就变成了 2.2 里那个问题。终止原因要记下来，并且算作一次失败，喂给断路器。

## 5. 速率类 vs 额度类：处理方式不一样

| | 速率类限制 | 额度类限制 |
|---|---|---|
| 例子 | 并发数、RPM、TPM | 日预算、月预算、套餐 token 数 |
| 性质 | **自己会恢复**（秒到分钟） | **累计的**，到重置时间才恢复 |
| 怎么处理 | 排队 / 等待，公平队列，每用户并发上限 | **直接拒绝**，明确告知「额度已用完」 |
| 排队的后果 | 合理，过一会儿就跑 | 无意义：队列越堆越长，重置后一起放出，制造尖峰 |
| 非关键任务 | 排后面 | 可降级到便宜模型 |
| HTTP | `429` + `Retry-After` | `402`（或 `403`/`429` + **明确错误码**）+ 重置时间 |

### 为什么额度用完不要返回「带 Retry-After 的 429」

很多客户端、SDK 看到 `429` 会自动退避重试。额度类问题再重试一千次也没用，只会制造重试风暴，还会让监控里看起来像「系统繁忙」。所以：

- 速率类：`429` + `Retry-After: 7`，告诉它「几秒后再来」；
- 额度类：换一个状态码或**至少换一个错误码**（如 `quota_exceeded`），带上 `reset_at`，**不带 `Retry-After`**；
- 断路器打开：`409`（或 `423`）+ `schedule_paused` + 恢复时间，让前端能提示「这个定时任务已暂停」。

具体状态码各家不统一（有的供应商额度用完也走 `429`，靠错误码区分），**重点是错误码要能让调用方区分「等一等」和「别等了」**。

### 取舍：排队 vs 直接拒绝 vs 降级

| | 排队 | 直接拒绝 | 降级到便宜模型 |
|---|---|---|---|
| 适合 | 速率类、短暂拥塞 | 额度类、队列已满 | 非关键任务、额度快见底 |
| 好处 | 不丢任务 | 快速失败、无积压 | 任务还能完成 |
| 代价 | 占内存、拉长延迟 | 用户要重试/等重置 | 质量下降，要想清楚哪些任务能降 |
| 翻车点 | 无界队列、额度类也排队 | 没有明确错误码 | 降级后依然死循环 |

## 6. 预占 + 结算：预算怎么扣

用户日预算有一个并发难点：十个 run 同时读到「还剩 $1」，都觉得自己能花，结果总共花了 $10。解决办法和 [10-16 的 `max_tokens` 预留](#/2026-10-16-llm-rate-limit-capacity) 是同一个思路：

1. **预占（reserve）**：调用前按**最坏情况**占额度：输入 token × 单价 + `max_tokens` × 单价。要用**一条原子语句**完成「没超额才加」；
2. **调用**；
3. **结算（settle）**：按实际 `usage` 算真实花费，**把差额退回**；调用失败就全额退回。

```sql
-- 预占：影响 0 行 = 超额，直接拒绝。检查和写入是同一条语句，并发安全
UPDATE user_budget
SET used_micro = used_micro + $2
WHERE user_id = $1 AND day = $3 AND used_micro + $2 <= limit_micro
RETURNING used_micro;

-- 结算：actual - reserved 通常是负数，即退款
UPDATE user_budget SET used_micro = used_micro + $2 WHERE user_id = $1 AND day = $3;
```

为什么一定要结算？demo 里算了一笔账：每步实际花 10,500 µ$，但最坏情况预占 21,000 µ$。**只预占不退差额，$1 的预算只能放行 47 步；预占 + 结算能放行 94 步**，吞吐差近一倍。

细节：

- **用户级和全局级两个计数器要一起扣。** 第二个扣失败时，要把第一个回滚（demo 里验证了回滚后用户计数没有虚增）；
- **金额用整数**（微美元 µ$），避免浮点误差；
- **按天分 key**（`budget:user:{id}:{day}`），次日自然是新的 key，不用写重置任务；
- 预占会让「额度即将见底时」略早拒绝一点（最坏情况高估），这是为了不超支付出的代价。如果任务运行中途才发现额度没了，已经花掉的部分就浪费了，所以长任务最好在**开始前**做一次准入检查。

## 7. 断路器：状态存哪？

断路器负责回答「同一个触发源，连续失败 N 次要不要停」。三个状态：

- **closed**（正常）：放行，失败就计数；
- **open**（暂停）：`paused_until` 之前一律拒绝，并通知用户；
- **half-open**（半开）：冷却到了，只放**一个**探测请求；成功回 closed，失败立刻回 open。

### 取舍：状态放哪

| 放哪 | 优点 | 缺点 | 用来做什么 |
|---|---|---|---|
| **只放进程内存** | 最快、最简单 | 重启丢、多实例各数各的（3 个实例各数到 1，永远到不了 N） | 只能当几秒的兜底缓存 |
| **数据库（权威）** | 持久、能事务、能审计、能给用户看「为什么被暂停」 | 比 Redis 慢 | **权威状态**：调度表里的字段 |
| **Redis（加速层）** | 快，计数 + TTL，冷却自动到期 | 可能丢，要能重建 | **热路径**：每次触发前判断要不要拦 |

**结论：** 权威状态放数据库，热路径用 Redis 做加速（丢了可以从数据库重建），进程内存只做几秒的兜底。

```sql
-- 调度表（schedules）里加这几列
--   consecutive_failures int not null default 0
--   paused_until         timestamptz
--   last_failure_at      timestamptz
--   last_error           text

-- 每个 run 失败时：原子加一，同时判断是否打开。不要先 SELECT 再 UPDATE
UPDATE schedules
SET consecutive_failures = consecutive_failures + 1,
    last_failure_at = now(),
    last_error = $2,
    paused_until = CASE WHEN consecutive_failures + 1 >= $3
                        THEN now() + interval '1 hour' ELSE paused_until END
WHERE id = $1
RETURNING consecutive_failures, paused_until;

-- 成功时清零
UPDATE schedules SET consecutive_failures = 0, paused_until = NULL WHERE id = $1;
```

### 为什么必须原子更新

先读后写：并发的两个 run 都读到 `2`，各自写 `3`，实际失败了 4 次却只记了 3 次。更糟的是并发很高时，**少算可能让计数永远到不了 N**，断路器形同虚设。demo 第 5 节让 100 个并发各加一次：先读后写最后只得到 **1**，原子 `incr` 得到 **100**。

### 容易漏的几个细节

- **key 用触发源（调度 id），不要用用户 id。** 用户 id 会连坐：他某个坏掉的定时任务把他其他正常的任务都停了；
- **只对「可重复的故障」计数。** 工具报错、被限流算；**用户主动取消不算**；
- **成功清零。** 「连续」失败才算，间隔着成功的不算；
- **半开要抢名额。** 多个实例同时发现冷却到了，只能放一个探测（Redis `SET NX`，或数据库 `INSERT ... ON CONFLICT DO NOTHING`），否则等于没有限制；
- **打开时通知用户，但只在第一次打开时通知。** 否则每次探测失败都发一封，变成骚扰。

## 8. 背压：队列要有界

排队只在速率类限制下合理，而且**队列必须有界**，否则排队只是把问题从「拒绝」换成「内存增长 + 延迟爆炸」。

- **长度上限：** 全局一个，**每用户一个**。热用户只能占满自己的份额，别人仍然能排进来；
- **等待时间上限：** 排太久的任务结果已经没有意义（用户早走了），直接拒绝比让它在后面悄悄超时好；
- **满了快速失败：** `429` + `Retry-After`。`Retry-After` 不用精确，粗估「排在前面的活 ÷ 并发 × 平均耗时」即可；
- **公平调度：** 空出名额时，优先给「正在跑的最少」的用户，并列时选等得最久的，别让一个用户的 100 个任务排在所有人前面；
- 客户端收到 `429` 要**带抖动的指数退避**，别全体在同一秒重试。

> **Dong 的结论：** 设置上限，达到就先拒绝。这就是背压的核心思想：与其让所有人一起慢，不如让一部分人快速知道「现在不行」。

## 9. Bad Case 翻车点

1. **只数重试次数**：LLM 一直调用成功的工具、重复同一动作，计数永远是 0，一夜烧光；
2. **只有 run 级上限，没有用户级预算**：每个 run 都不超限，但同一个用户开了 500 个，总数照样烧穿；
3. **定时任务失败后自动新建 run，没有断路器**：整晚每分钟一个新 run，每个都「合规地」烧一点；
4. **额度用完返回带 `Retry-After` 的 `429`**：客户端自动重试，形成重试风暴；
5. **额度类限制也排队**：队列无限增长，额度重置时一起放出，尖峰把速率限制又打爆；
6. **无界队列**：内存涨、延迟涨，用户早就走了，任务还在后面白白跑；
7. **断路器计数放内存**：重启清零、多实例各数各的，永远数不到 N；
8. **先读后写更新计数/预算**：并发时少算，护栏形同虚设；
9. **断路器 key 用用户 id**：一个坏任务连坐停掉用户所有任务；
10. **用户取消也算失败**：用户多点几次停止，自己的调度被暂停；
11. **全局预算当主防线**：触发时已经烧完，而且所有人一起被拒；
12. **预占只按平均值**：模型一次输出超出预期，实际超支；要按 `max_tokens` 这种硬上限预占。

## 10. Review 审 AI 方案时问什么

1. 一个 run 最多能跑多少步、花多少钱、多长时间？这几个数字写在哪？
2. 工具全部成功但模型一直重复同一动作，哪个机制会停下来？
3. 同一个用户一晚上开 500 个 run，谁来封顶？封顶的数字是预占还是事后统计？
4. 定时任务/自动重建的 run，失败后会不会无限重新触发？断路器在哪？
5. 额度用完和系统繁忙，返回给调用方的是同一种错误吗？客户端会自动重试吗？
6. 队列有长度上限和等待时间上限吗？满了是排队、拒绝还是丢弃？
7. 失败计数、预算计数存在哪里？重启、多实例之后还对吗？是原子更新吗？
8. 一个用户把自己的额度烧光，其他用户受影响吗？

## 11. Demo 说明

`demos/2026-10-24-llm-cost-guardrails/`：纯 TypeScript，**无需联网、无需真实 LLM**（LLM、工具、时钟都是 mock），`bash test.sh` 一键运行，最后打印 `ALL PASS`。

| 文件 | 内容 |
|---|---|
| `store.ts` | **状态存取接口** `StateStore`（`incr` / `incrIfBelow` / `setIfAbsent`）+ 内存 Map 实现，注释里写了对应的 SQL / Redis 命令 |
| `errors.ts` | 三类拒绝的 HTTP 语义：`429`+`Retry-After`、`402` 额度用完、`409` 调度暂停 |
| `budget.ts` | 用户/全局日预算，**预占 + 结算**，全局扣失败时回滚用户计数 |
| `run-guard.ts` | 单 run 护栏：步数 / 花费 / token / 时长 / 重复动作 / 工具连续报错 |
| `scheduler.ts` | 并发上限 + **有界公平队列**，满了抛 `429`，排队超时也拒绝 |
| `breaker.ts` | 断路器：连续失败暂停，成功清零，冷却后半开探测，用户取消不计数 |

## 12. 复习题

**1. 为什么只数「重试次数」拦不住 Agent 死循环？应该加哪些上限？**

<details><summary>参考答案</summary>

- 工具调用都成功、LLM 只是重复同一动作时，重试计数永远是 0；
- run 级要加：**总步数、总 token、总花费、总时长**四个硬上限，再加**重复动作检测**和**工具连续报错**上限；
- 重复检测是启发式（参数一变就被绕过），硬上限才是底线。

</details>

**2. 四层护栏（单步 / 单 run / 用户租户 / 全局）各自管什么？只加其中一层会漏什么？**

<details><summary>参考答案</summary>

- 单步：`max_tokens`、输入裁剪，漏「一万次小请求」；
- 单 run：步数/花费/时长/重复，漏「开 500 个 run」；
- 用户/租户：并发、日预算、队列份额，漏「全体用户同时涨」；
- 全局：全局预算、供应商硬上限，只是保险，触发时通常已经烧完且所有人一起被拒；
- 死循环发生在 run 层，所以先加 run 层，再用用户级给「一个人」的损失封顶。

</details>

**3. 速率类限制和额度类限制各举两个例子，处理方式有什么不同？**

<details><summary>参考答案</summary>

- 速率类：并发数、RPM/TPM，过一会儿自己恢复 → 排队/等待，返回 `429` + `Retry-After`；
- 额度类：日预算、月预算，累计、重置前不恢复 → 直接拒绝，返回明确的额度错误码和重置时间，非关键任务可降级到便宜模型；
- 额度类排队没意义：队列只会越堆越长，额度重置后一起放出，反而造成新的尖峰。

</details>

**4. 额度用完时为什么不应该返回带 `Retry-After` 的 `429`？**

<details><summary>参考答案</summary>

- 很多客户端/SDK 看到 `429` 会自动退避重试，额度类问题重试一千次也没用，只会制造重试风暴；
- 应换状态码（如 `402`）或至少换错误码（`quota_exceeded`），带上 `reset_at`，不带 `Retry-After`；
- 目标是让调用方能区分「等一等」和「别等了」。

</details>

**5. 「预占 + 结算」是什么？为什么不只预占？**

<details><summary>参考答案</summary>

- 预占：调用前按最坏情况（输入 + `max_tokens`）原子地占额度，超额直接拒绝；
- 结算：调用后按实际 `usage` 算，把差额退回；失败则全额退回；
- 只预占会让额度被高估的最坏情况占住，吞吐大幅下降（demo 里只有一半）；
- 预占必须是一条原子语句（`UPDATE ... WHERE used + x <= limit`），否则并发时会超支。

</details>

**6. 断路器连续失败次数记在哪里？为什么不能只放内存？**

<details><summary>参考答案</summary>

- 权威状态放数据库（调度表的 `consecutive_failures`、`paused_until`、`last_failure_at`、`last_error`）；
- 热路径用 Redis 计数 + TTL 加速，丢了可以从数据库重建；
- 进程内存只能做几秒的兜底缓存；
- 只放内存：重启清零；多实例各数各的，永远数不到 N。

</details>

**7. 为什么失败计数必须用原子更新？怎么写？**

<details><summary>参考答案</summary>

- 先读后写：并发的两个 run 都读到旧值，各自写旧值 + 1，少算一次；并发高时可能永远到不了 N；
- 用 `UPDATE ... SET n = n + 1 ... RETURNING n`（Redis 用 `INCR`），检查和写入在同一条语句里；
- 同理，预算的「没超额才加」也要写成一条条件更新。

</details>

**8. 断路器的 key 用用户 id 还是调度 id？哪些失败该计数？**

<details><summary>参考答案</summary>

- 用触发源（调度 id）：用户 id 会连坐，一个坏任务停掉他的所有正常任务；
- 只对**可重复的故障**计数：工具报错、被限流；用户主动取消不算；
- 成功清零，只有「连续」失败才算。

</details>

**9. 断路器的「半开」是什么？为什么只放一个探测？**

<details><summary>参考答案</summary>

- 冷却结束后不直接恢复，只放一个探测请求：成功 → 回 closed 并清零，失败 → 立刻回 open（不用再数 N 次）；
- 只放一个，是因为如果服务还没好，放一堆请求就是再来一次洪峰；
- 多实例下要靠原子的 `SET NX` / `ON CONFLICT DO NOTHING` 抢探测名额。

</details>

**10. 队列为什么必须有界？满了怎么办？还应该限制什么？**

<details><summary>参考答案</summary>

- 无界队列把「拒绝」换成「内存增长 + 延迟爆炸」，用户早走了任务还在白跑；
- 设全局长度上限、每用户长度上限（热用户只占自己的份额）、等待时间上限；
- 满了快速拒绝，`429` + `Retry-After`，这叫背压；
- 客户端用带抖动的指数退避重试，别同一秒全部重来。

</details>

**11. 追问：用户的定时任务每分钟触发，每次 run 都失败，整晚会发生什么？你加什么？**

<details><summary>参考答案</summary>

- 没有断路器：8 小时 480 个 run，每个都在自己的 run 级上限内「合规」，总共烧掉 480 倍；
- 加断路器：连续失败 3 次暂停，通知用户，冷却后半开探测；demo 里同样场景只跑了 10 个 run；
- 同时用户级日预算兜底：即使断路器有 bug，预算也会封顶。

</details>

**12. 追问：run 被护栏终止之后，该不该让调度器自动新建 run 接着做？**

<details><summary>参考答案</summary>

- 不该。这等于把死循环从 run 内部搬到 run 外部；
- 护栏终止要记下原因并算一次失败，喂给断路器；
- 要继续只能由用户确认，或者换一种策略（换提示词、换模型、人工介入）再开新 run。

</details>
